# Groundwater Forecast

This project forecasts groundwater levels for four monitoring stations in Pune district using historical groundwater observations, rainfall, lagged measurements, and seasonal features. It exposes forecasts and related station status, alerts, anomalies, recharge summaries, and what-if scenarios through a FastAPI service.

## Data sources and limits

### Data sources

- **Groundwater observations:** India-WRIS and the Central Ground Water Board (CGWB) are the credited sources for groundwater information.
- **Rainfall:** India Meteorological Department (IMD) is the credited rainfall source. The processed rainfall dataset uses historical data for 2023–2025 and available real-time data from 1 January through 30 June 2026.
- Processed rainfall data use the columns `station_id`, `date`, and `rain`. The current dataset is intended to cover four stations.

Confirm the exact source, coverage, units, and download/update dates against the source files and metadata before reproducing the project.

### Data limitations

- The current project covers only four stations in Pune district; results may not generalize to other regions or aquifers.
- The available rainfall period and groundwater observation history are limited. Missing, stale, or repeated station readings can reduce forecast reliability.
- Rainfall coverage and groundwater observations may not align perfectly in time or location.
- Evaluation results describe the current dataset and evaluation setup; they do not guarantee accuracy at new stations or in future periods.
- Risk thresholds are generated by the current pipeline and require separate validation before being used for operational groundwater decisions.
- The what-if endpoint produces a simulated scenario by scaling the predicted change; it is not a separately trained machine-learning forecast.

## Setup

Run these commands from the repository root. Use a Python version compatible with the dependencies in `requirements.txt`.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

If you open a new terminal later, activate the environment again:

```bash
source .venv/bin/activate
```

## Run order

Run the following commands from the repository root, in this order:

```bash
python -m src.stations
python -m src.rain
python -m src.data
python -m src.train
uvicorn app.main:app --reload
python -m pytest -q
```

The first commands prepare station, rainfall, and modelling data; `src.train` trains and evaluates the model; Uvicorn starts the API; and pytest runs the test suite. The API server stays in the foreground while it is running. To run tests in a separate terminal, activate `.venv` there as well.

When the API is running, interactive documentation is available at `http://127.0.0.1:8000/docs` and the OpenAPI schema at `http://127.0.0.1:8000/openapi.json`.

## API integration for frontend developers

### Base URL

When the backend is running locally, use:

```text
http://127.0.0.1:8000/api/v1
```

For example, the stations endpoint is `GET http://127.0.0.1:8000/api/v1/stations`.

The examples below illustrate the response structure. Actual station IDs, dates, levels, and values depend on the generated dataset and current model output. Use `/docs` or `/openapi.json` as the source of truth if the running API differs.

### Endpoint reference

All endpoints are prefixed with `/api/v1`.

| Method | Endpoint                           | Query/body                                                                                           | Purpose                                                                     |
| ------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `GET`  | `/health`                          | None                                                                                                 | Health check.                                                               |
| `GET`  | `/model`                           | None                                                                                                 | Selected model name and evaluation metrics.                                 |
| `GET`  | `/stations`                        | None                                                                                                 | Station list with coordinates, latest level, and risk.                      |
| `GET`  | `/stations/{station_id}/status`    | Optional `days` query parameter; defaults to `30` and must be within the configured maximum horizon. | Current status, trend, risk, forecast change, data age, advice, and alerts. |
| `GET`  | `/stations/{station_id}/forecast`  | Optional `days`; defaults to `30`.                                                                   | Recent observations and forecast points.                                    |
| `GET`  | `/stations/{station_id}/history`   | Optional `start` and `end` dates, formatted `YYYY-MM-DD`.                                            | Historical observed levels.                                                 |
| `GET`  | `/stations/{station_id}/alerts`    | None                                                                                                 | Alert messages for a station.                                               |
| `GET`  | `/stations/{station_id}/anomalies` | None                                                                                                 | Detected anomalous observations/events.                                     |
| `GET`  | `/stations/{station_id}/recharge`  | None                                                                                                 | Yearly recharge-related summaries.                                          |
| `POST` | `/whatif`                          | JSON body shown below.                                                                               | Simulated usage scenario compared with baseline.                            |

### Example responses

#### `GET /stations`

Returns a JSON array. Fields shown here match the station response schema:

```json
[
  {
    "id": "C",
    "name": "Example station",
    "district": "Pune",
    "lat": 18.5,
    "lon": 73.8,
    "level": 12.4,
    "risk": "WATCH"
  }
]
```

The station name, coordinates, level, and risk above are illustrative, not actual measurements.

#### `GET /stations/C/status?days=30`

The status response includes fields like these:

```json
{
  "station_id": "C",
  "as_of": "2026-06-30",
  "level": 12.4,
  "trend": "stable",
  "risk": "WATCH",
  "days": 30,
  "data_age_days": 0,
  "forecast_level": 12.1,
  "change_m": -0.3,
  "advice": "Example advice",
  "alerts": []
}
```

This is a structural example only. Dates, values, advice, and risk are illustrative. `as_of` is the date of the latest observation. `data_age_days` reports how many days old that observation is. `change_m` is the forecast level minus the current level, in metres.

Possible `risk` values are `SAFE`, `WATCH`, `CRITICAL`, and `UNKNOWN`. The `trend` field can be `declining`, `stable`, `improving`, or `unknown`. `UNKNOWN` means the service cannot reliably assign a risk category, for example when observations are stale or stuck, or the requested forecast horizon is unavailable.

#### `GET /stations/C/forecast?days=30`

The response contains `observed` and `forecast` arrays. Each point has a date and level:

```json
{
  "station_id": "C",
  "observed": [
    { "date": "2026-06-28", "level": 12.3 },
    { "date": "2026-06-29", "level": 12.4 }
  ],
  "forecast": [
    { "date": "2026-07-01", "level": 12.35 },
    { "date": "2026-07-02", "level": 12.32 }
  ]
}
```

The shortened arrays and values are illustrative; the real response can contain more points depending on the requested horizon and available history.

#### `GET /stations/C/history?start=2026-01-01&end=2026-06-30`

```json
{
  "station_id": "C",
  "observed": [
    { "date": "2026-06-29", "level": 12.4 },
    { "date": "2026-06-30", "level": 12.4 }
  ]
}
```

The dates and values are illustrative. If `start` or `end` is omitted, that side of the date range is not filtered.

#### `GET /stations/C/alerts`

```json
{
  "station_id": "C",
  "alerts": ["Groundwater data is stale."]
}
```

Alert text depends on the station's data and current status; the message above is illustrative.

#### `GET /stations/C/anomalies` and `GET /stations/C/recharge`

These endpoints return `events` and `years` arrays, respectively. See `/docs` for the exact response fields and current examples generated by the running service.

#### `POST /whatif`

Request body:

```json
{
  "station_id": "C",
  "usage": "medium",
  "days": 30
}
```

`usage` must be `low`, `medium`, or `high`; `days` must be between 1 and 30 according to the current request schema. Confirm that the chosen station ID exists in the current dataset.

Example response structure:

```json
{
  "simulated": true,
  "note": "Simulated scenario, not an ML forecast: usage scales the predicted change.",
  "baseline": [{ "date": "2026-07-01", "level": 12.35 }],
  "scenario": [{ "date": "2026-07-01", "level": 12.35 }]
}
```

The values and dates are illustrative. Treat `scenario` as a simulated comparison, not a separately trained prediction.

### Frontend connection (React/Vite or another browser client)

1. Start the backend using `uvicorn app.main:app --reload`.
2. Confirm that `http://127.0.0.1:8000/docs` loads and that the endpoints work.
3. Set the frontend API base URL to `http://127.0.0.1:8000/api/v1` for local development. Avoid scattering this URL throughout the code; keep it in one configuration file or environment variable.
4. Fetch data from the API rather than hardcoding example values. Show loading and error states while requests are in progress or fail.
5. Handle `UNKNOWN` as its own status. Do not present it as `SAFE`, and show the API's alerts/advice when available.
6. Check the browser console if requests fail. A frontend served from another origin (for example, Vite at `http://localhost:5173`) may require CORS permission in FastAPI. Check `app/main.py` for existing CORS middleware and allow only the frontend origins needed for development/deployment.
7. Use `/docs` and `/openapi.json` to verify exact schemas. These live API definitions take precedence over illustrative examples in this README.

### Example frontend fetch

```javascript
const API_BASE = "http://127.0.0.1:8000/api/v1";

export async function getStationStatus(stationId, days = 30) {
  const response = await fetch(
    `${API_BASE}/stations/${encodeURIComponent(stationId)}/status?days=${days}`,
  );

  if (!response.ok) {
    throw new Error(`Status request failed: ${response.status}`);
  }

  return response.json();
}
```

This example assumes the frontend and backend are running on the same computer. For deployment, configure the API base URL for the deployed backend rather than using `127.0.0.1`.

## Dashboard (frontend)

`frontend/` contains the Jal Setu dashboard (plain HTML/CSS/JS, no build step). `frontend/serve.py` serves it and forwards `/api/*` requests to the backend, so no CORS setup is needed.

Run the backend and the dashboard in two terminals:

```bash
uvicorn app.main:app --reload     # backend on port 8000
python frontend/serve.py          # dashboard on http://127.0.0.1:5500/
```

The API base URL is set in `frontend/config.js`.

### Publishing on GitHub Pages

`.github/workflows/pages.yml` publishes the dashboard on every push to `main` (and once a day). It trains the model from `data/processed/`, runs `frontend/export_static.py` to save every API response the dashboard uses as JSON, and deploys the result to GitHub Pages. The backend code is unchanged; the published site is a static build of its responses.

One-time setup (repository admin): **Settings → Pages → Build and deployment → Source: GitHub Actions**. The site is then at `https://<owner>.github.io/<repo>/`.

To build it locally: `python -m src.train && python frontend/export_static.py` (writes `dist/`).

## Results

The current training output compares Ridge and Gradient Boosting Regressor (GBR) with a persistence baseline at 7-, 14-, and 30-day horizons. Persistence predicts that the groundwater level remains at its latest observed value.

| Forecast horizon | Ridge MAE | GBR MAE | Persistence MAE |
| ---------------- | --------: | ------: | --------------: |
| 7 days           |   0.248 m | 0.196 m |         0.271 m |
| 14 days          |   0.423 m | 0.385 m |         0.462 m |
| 30 days          |   0.545 m | 0.636 m |         0.663 m |

Ridge is the selected overall model in the current training output. At 30 days, Ridge's MAE is 0.545 m compared with 0.663 m for persistence, an absolute reduction of 0.118 m (11.8 cm), or approximately **17.8% lower MAE** than persistence. GBR has lower MAE at 7 and 14 days, while Ridge performs better at 30 days.

The current pipeline reported 30-day change thresholds of approximately 0.464 m for `watch` and 1.120 m for `critical`. These are pipeline outputs, not independently validated operational thresholds.

### Feature ablations

Feature ablation experiments were run by changing the `FEATURES` list while keeping `make_features()` unchanged. The selected feature configuration is the one currently recorded in `src/features.py`. Re-run the ablations when adding stations or years of data, and record the feature list and metrics for each run so results remain reproducible.

## Limitations

- This is a small, geographically limited dataset; evaluation metrics may be unstable and should be interpreted cautiously.
- Forecast errors increase with horizon, and no model beats every alternative at every horizon.
- A model outperforming persistence on this evaluation does not establish that it will outperform persistence at every station, season, or future period.
- Data freshness and stuck-reading checks are engineering safeguards with initial thresholds; they should be calibrated to the actual station reporting frequency.
- Risk classifications, recharge summaries, anomaly detections, and what-if scenarios are decision-support outputs, not substitutes for official hydrogeological assessment.
- Do not use these outputs alone for high-impact water-management decisions without independent validation and domain review.
